제출이 5회뿐이라는 게 이후 모든 규칙의 이유다. 아무거나 내볼 수 없으니
**무엇을 낼지 근거를 갖고 정해야** 하고, 그래서 자체 검증셋과 실험 기록이 필요하다.

## 2. 우리가 만드는 것

```
입력:  차 지붕 카메라 6대의 사진 (앞·뒤·좌·우 360도)
       + "직진 / 좌회전 / 우회전" 지시
        |
        v
     [ 모델 ]
        |
        v
출력:  0.5 / 1.0 / 1.5 / 2.0 / 2.5 / 3.0초 뒤 차의 위치 6개 (x, y)
```

**End-to-End 라는 말의 뜻**: 보통은 "차선 인식 -> 물체 인식 -> 경로 계획"을
따로 만들어 이어 붙인다. E2E 는 **사진을 넣으면 경로가 바로 나오는 하나의 신경망**이다.
중간 단계를 사람이 설계하지 않는다.

## 3. 데이터

```
학습용  376개 시나리오
        1개 = 40초 주행 (300프레임 x 카메라 6대)
        정답 궤적 + 3D 물체 박스 + 차선 정보

평가용  1,125개 클립
        클립마다 "지금 이 순간" 하나에 대해 3초 뒤까지 예측
```

원본은 **284GB** 다. 그대로 쓰기 어려워서 전처리를 했다.

### 전처리 (이미 끝났다)

원본 파이프라인은 매 학습 스텝마다 이 네 가지를 반복했다.

```
1920x1536 사진 18장 읽기 -> 렌즈 왜곡 펴기 -> 자르기 -> 768x432 로 줄이기
```

**이 네 단계에는 무작위 요소가 없다.** 같은 사진이면 언제나 같은 결과다.
그런데 60 epoch x 11만 샘플 = **676만 번** 반복하고 있었다. 한 번만 계산해서 저장했다.

| | 원본 | 전처리 후 |
|---|---|---|
| 용량 | 284 GB | **48 GB** |
| 1 epoch | 21시간 | **12시간** |

> **주의**: 사진을 자르고 줄이면 카메라 파라미터도 같이 고쳐야 한다.
> 안 고치면 3D 물체가 사진의 엉뚱한 곳에 찍히는데 **에러가 나지 않는다.**
> 학습은 멀쩡히 돌고 loss 도 떨어지지만 모델이 틀린 대응을 배운다.
> 수치(오차 1.09e-11 px)와 눈(사진 위에 박스·차선 그리기)으로 두 번 검증했다.
> 자세한 건 [DATA.md](DATA.md).

**전처리 파라미터를 바꾸면 실험 비교가 불가능해진다.** 받은 데이터를 그대로 쓸 것.

## 4. 점수 계산 — 여기가 핵심

예측한 6개 점과 정답의 거리를 재는데 방식이 특이하다.

```
1초 점수 = 앞 2개 점(0.5, 1.0초)의 평균 오차
2초 점수 = 앞 4개 점의 평균 오차
3초 점수 = 6개 전부의 평균 오차
최종     = 이 셋의 평균          (낮을수록 좋다)
```

앞쪽 점은 세 번 다 들어가고 뒤쪽 점은 한 번만 들어간다. 풀어보면:

| | 0.5초 | 1.0초 | 1.5초 | 2.0초 | 2.5초 | 3.0초 |
|---|---|---|---|---|---|---|
| 점수 기여 | **30.6%** | **30.6%** | 13.9% | 13.9% | 5.6% | 5.6% |

> **0.5초와 1.0초 두 점이 점수의 61% 를 차지한다.**
> 3초 뒤를 정확히 맞히려고 애쓰는 건 효율이 나쁘다.

## 5. 대회 규정 — 모르면 실격이다

2026-08-19 운영국 공지.

```
금지  과거 궤적으로 속도를 구해 "이대로 가면 여기쯤" 계산하기
      -> 신경망으로 감싸도 똑같이 금지
      -> 위반 시 순위 제외, 경중에 따라 팀 실격

필수  과거 정보를 쓰는 모든 프레임에 그 프레임 영상도 함께 입력되어야 함

허용  자차 속도, 5초 뒤 목표 지점을 "보조 입력"으로 쓰는 것
```

판정 기준은 **구현 형태가 아니라 "성능의 실질적 출처"** 다.

### 왜 이런 공지가 나왔나

직접 측정해봤다. **모델 없이 "지금 속도 그대로 직진"만 계산해도 0.414** 가 나온다.
현재 리더보드 3위가 **0.398** 이다. 1·2위는 0.077 인데 정상적인 방법으로 나올 수 있는
값이 아니다.

> **우리 방침: 리더보드 상위권을 목표로 잡지 않는다.**
> 저 점수들은 심사에서 걸러질 가능성이 높고, 따라가면 우리도 실격이다.
> **제대로 된 카메라 기반 모델의 실제 성능은 아직 아무도 모른다.**
> 그걸 우리가 먼저 확보하는 게 목표다.

자차 상태나 목표점을 입력에 넣은 모델은 **제출 전에 반드시** 영상 기여도를 잰다.

```bash
python tools/ablate_image.py <config> <checkpoint> --scenarios 10
```

영상을 지우거나 다른 장면으로 바꿔 넣고 점수가 얼마나 나빠지는지 본다.
**악화가 20% 미만이면 영상을 안 보고 있다는 뜻이라 제출하지 않는다.**

## 6. 쓰는 모델

**VAD** (ICCV 2023). 주최측이 준 베이스라인이다.

| | |
|---|---|
| 파라미터 | 약 4,000만 개 |
| FLOPs | 446 G (제한 7,053 G 라 여유 충분) |

한 문장으로: **여러 카메라 사진을 위에서 내려다보는 지도(BEV)로 바꾸고,
그 위에서 주변 차량과 차선을 파악한 뒤 갈 길을 정하는 모델**이다.

**모델 구조는 건드리지 않는다.** 주최측이 준 걸 그대로 쓰고 학습 방법과 입력만 바꾼다.
대회 경험자 조언이기도 하고, 구조를 바꾸면 버그가 조용히 성능만 갉아먹는다.

## 7. 지금 돌고 있는 실험 2개

### 실험 1 — 베이스라인 (메인컴)

**아무것도 안 바꾸고 그대로 돌린다.**

싱거워 보이지만 가장 중요하다. **기준점이 없으면 "좋아졌다"는 말 자체가 성립하지 않는다.**
앞으로 모든 실험이 이 숫자와 비교된다. 순수 카메라 모델이라 규정 논란이 전혀 없어서
**첫 제출 후보로 가장 안전하다.**

### 실험 2 — 손실 시간 가중치 (서브컴)

4장에서 본 대로 **점수는 앞쪽 점을 1.8배 중요하게 본다.**
그런데 **학습은 6개 점을 똑같이 취급하고 있었다.**

시험 배점이 다른데 전 과목을 똑같이 공부하는 셈이다. 배점에 맞춰 앞쪽을 더 중요하게
학습하도록 손실 가중치를 바꿨다.

> **함정 하나**: 모델이 내놓는 건 누적 좌표가 아니라 **한 스텝씩의 이동량**이다.
> 첫 이동량이 틀리면 이후 6개 점이 전부 틀어진다. 그래서 배점 `[11,11,5,5,2,2]` 를
> 그대로 쓰면 안 되고 **뒤에서부터 누적한 `[36,25,14,9,4,2]`** 를 써야 한다.

구조 변경이 없어서 베이스라인과 직접 비교 가능하다.
config: `projects/configs/VAD/exp_jeung_0819_timeweight.py`

## 8. 일정

```
8/24        두 실험 완료 -> 1회차 제출
            (자체 검증 점수와 리더보드 점수의 관계를 확인하는 게 목적)
8/24~9/10   본 실험
9/10~9/18   최종 후보 재학습
9/18~9/23   버퍼 - 제출 검증, 2차 제출물 준비
```

**마지막 5일은 반드시 비워둔다.** 제출 형식 오류는 `[0,0]` 으로 채점되고
참가자 책임이다.

전체 학습 1회가 5일이다. 그래서 **"10 epoch 이 정말 필요한가"** 를 일찍 아는 게
무엇보다 중요하다. 6 epoch 로 충분하다면 남은 기간에 돌릴 수 있는 실험 횟수가
두 배 가까이 차이난다.

### 학습 걸기 전에 꼭 확인할 것

```python
checkpoint_config = dict(
    type='IterSafeCheckpointHook', by_epoch=False, interval=1000, max_keep_ckpts=3)
```

`interval=1` 로 두면 **"1 epoch 마다"** 라는 뜻이다. 1 epoch 이 11시간이라
그 전에 죽으면 아무것도 안 남는다. 실제로 5시간 20분치를 날린 적이 있다.

그리고 **VRAM 은 90% 를 넘기지 않는다.** 브라우저 같은 것도 GPU 를 쓴다.
배치를 하나 줄여 2GB 정도는 비워두는 게 낫다.
