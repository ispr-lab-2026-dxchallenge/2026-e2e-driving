4명이 각자 돌리면 한 주만 지나도 **어떤 설정이 무슨 결과를 냈는지 아무도 모르게 된다.**
그리고 제출이 **팀당 5회**뿐이라, 무엇을 제출할지 근거를 갖고 정해야 한다.

## 0. 챌린지 규정 — 무엇을 만들기 전에 먼저 읽을 것

2026-08-19 운영국 공지. **위반 시 순위 제외, 경중에 따라 팀 실격.**
아이디어가 떠오르면 config 를 짜기 전에 이 절과 대조할 것.

### 판정 기준은 "구현 형태"가 아니라 "성능의 실질적 출처"다

수식으로 짜든 신경망으로 짜든 똑같이 본다.
**자차의 과거 상태와 목표 지점만으로 궤적이 결정되는 구성은 신경망이어도 금지**다.
최종 궤적은 영상 인식 결과에서 나와야 하고, 과거 상태와 목표 지점은 **보조 입력**에 한한다.

### 금지

| | 내용 |
|---|---|
| §3-2 | 과거 궤적에서 속도·가속도를 뽑아 등속/등가속/다항회귀로 미래 궤적을 만드는 것 |
| §3-2 | 특정 프레임에서 자차 정보만 쓰고 **그 프레임의 영상은 안 쓰는** 구성 |
| §3-3 | 영상 인식을 거치지 않는 규칙·수식 기반 궤적 산출 (신경망 형태여도 동일) |
| §3-1 | 목표 지점만으로 궤적 생성, 다른 클립과 대조해 제공 범위 밖 미래를 복원 |

### 허용

- **자차 과거 상태**(속도·요레이트 등)를 **보조 입력**으로 넣는 것
- **5초 목표점**을 goal conditioning 으로 넣는 것 — "내비 목적지와 동일한 성격"이라 명시

### §4 영상 입력 의무

> 과거 정보를 활용하는 **모든 프레임**에 대해 그 프레임의 영상이 반드시 모델 입력으로
> 함께 사용되어야 하며, 최종 궤적은 그 영상을 소비하는 모델의 추론 결과여야 한다.

VAD 는 매 프레임 카메라 6대를 넣고 궤적이 모델 출력이므로 이 조건을 만족한다.

### 추가 확정 사항 (2026-08-25 운영국 질의응답)

타 팀 질의에 대한 운영국 답변으로 경계선이 더 명확해졌다.

| 기법 | 판정 |
|---|---|
| 모델 출력을 제출 규격으로 바꾸는 후처리 (cumsum, 모드 선택 등) | 허용. **T_infer 에도 미포함** |
| 신경망에 입력되지 않은 정보를 쓰는 후처리 (운동학 보정·하이브리드) | **금지** |
| 과거 pose 로 현재 속도·요레이트 계산 | 허용. **그 프레임 영상까지 입력할 필요 없음** (베이스라인 방식) |
| 목표점을 condition 입력으로 (방향·후보 선택에 영향) | 허용 |
| **목표점 + 자차 상태만으로 최종 궤적 생성** | **금지** — 영상 인식과 무관하게 경로를 결정하면 안 된다 |

같은 날 추가 답변 (추론 최적화·측정 절차):

| 항목 | 확정 내용 |
|---|---|
| 이력 프레임 부분 forward | **허용** — BEV 생성까지만 하고 head 생략 가능. 실측 T_infer -21%, L2 완전 동일 |
| fp16/bf16 추론 | **허용.** TensorRT 는 2차 측정 시 불가할 수 있어 비추천 |
| T_infer 절차 | 임시 데이터로 warm-up 후 **clip 별 forward 시간의 평균**. batch 1 고정, `cuda.synchronize` 적용, **데이터는 VRAM 에 있는 상태**로 forward 만 측정 |
| 다중 모드에서 command 로 선택 | 허용 (베이스라인 방식) |
| 목표점·기준점으로 **후보 선택** | 허용 — 단 선택까지만. 그걸로 궤적을 생성·보정하면 금지 |

`tools/etri_test_submit.py` 는 history-bev-only + fp16 이 **기본으로 켜져** 있다
(실측 T_infer -42%). 되돌리려면 `--full-forward --fp32`.

같이 확정된 것:

- **T_infer 는 "model forward 만" 계산한다.** JPEG 디코딩·규격 변환은 미포함.
  `tools/eval_protocol.py` 의 측정 방식이 공식 정의와 일치한다
- §4(영상 입력 의무)는 pose 차분으로 속도를 구하는 경우까지 확장 적용되지 않는다.
  문자 그대로 읽으면 과거 영상이 필수로 보였지만, 운영국이 명시적으로 완화했다

> 자차 상태를 입력에 넣는 실험이 특히 유의할 것: "target point 와 자차 상태만으로
> 최종 궤적을 생성"하는 구성은 금지라고 **명시**됐다. 학습 손실이 유난히 빨리
> 떨어지면 모델이 그 방향으로 수렴하고 있다는 신호일 수 있다. ablation 필수.

### 결정적 확정 (2026-08-27 운영국) — 구조 기반 금지

판정이 결과(ablation)가 아니라 **구조**로 내려진다는 것이 명시됐다.

> "판정 기준은 과거 궤적이나 status 가 **planner 에 직접 또는 단순 임베딩으로
> 입력**되어 최종궤적을 출력하는 여부에 결정됩니다. ...
> **과거 정보를 직접적으로 planner 입력으로 또는 단순 임베딩 형태로 사용하는
> 것을 금지**하며, 여러 task 의 공통 특징을 향상하는 등의 **간접적 활용은 허용**"

운영국이 예시로 든 "베이스라인이 지원하지만 기본으로 안 쓰는 구조"가 바로
`ego_his_encoder` / `ego_lcf_feat_idx` 다. **이 통로는 켜는 것 자체가 금지다.**
ablation 을 통과해도 코드 심사에서 걸린다.

이에 따라 폐기된 실험:
- `exp_jeung_0818_egostate` (속도 -> planner 직접 입력)
- `exp_target_vel_0824` (목표점+속도, epoch 7 에서 중단)
- `exp_target_0824` (목표점 단독 — 같은 직접 입력 통로 + ablation 0.94배 실패.
  단 val L2 0.331 로 **목표점 정보의 가치(~0.22 개선분)는 확인**됐다)

### 목표점 최종 확정 (2026-08-28 질의 답변)

> "미래도 동일합니다. 다만 ... **모델의 여러 출력 중 선택에만 활용되는 경우는 허용**"

목표점도 과거 정보와 같은 규칙을 적용받는다. **궤적 생성에 기여하는 어떤
입력(직접·단순 임베딩·간접 조건화 포함)도 불가**하고, 허용은 "모델 출력 중
선택"뿐이다.

선택 방식은 실측 완료 — 후보 3개(command 모드)로는 이득이 없다
(0.5537 -> 0.5690, RESULTS.md #8). 목표점의 가치(~0.22)를 꺼내려면 모델이
후보를 훨씬 다양하게 내놓아야 하는데(VADv2 식 vocabulary) 구조 변경 비용이
크므로 보류한다.

**결론(8/28 갱신): 전장은 두 개다 — ① 순수 비전 모델의 품질, ② 학습 데이터 유래 앵커 + 영상 기반 선택·보정 (운영국 공인 패턴).**

### 허용 패턴 최초 명시 (2026-08-28 후속 답변) — 앵커 방식 공인

타 팀의 "수식 기반 궤적 + 네트워크 보정" 질의에 대한 답변에서, 운영국이
처음으로 **허용되는 구조를 구체적으로 서술**했다.

> (금지) "각 테스트 clip 의 과거 데이터로 궤적을 직접 산출하여 이를 영상과
> 네트워크를 통해 보정하는 형태" — 공통 원칙 위반
>
> (허용) "**학습 데이터를 활용하여 생성한 고정 앵커** 중에서 **영상 인식으로
> 선택하는 방식** ... 테스트 데이터의 과거 정보를 궤적 생성에 사용하지 않고
> 학습 데이터에서 후보를 생성한 뒤 **영상 기반으로 선택 및 보정**하는 방식"

이로써 판정 기준이 최종적으로 명확해졌다:

| 궤적(후보)의 출처 | 선택·보정의 근거 | 판정 |
|---|---|---|
| 테스트 clip 의 과거/미래 정보 (수식이든 신경망이든) | 무엇이든 | **금지** |
| **학습 데이터에서 만든 고정 앵커** | **영상 인식** | **허용 (명시)** |

**전략적 의미**: 보류했던 vocabulary(앵커 사전 + 비전 점수화) 방식이 운영국
공인 패턴이 됐다. "선택 및 보정"까지 허용 서술에 포함되어, 앵커 위에
영상 기반 보정 회귀를 얹는 것도 가능하다. 사전 계산으로 확인해 둔 상한:
앵커 K=4096 이면 오라클 L2 0.074 (기록: RESULTS.md).
단, 선택·보정의 근거는 영상이어야 하며 목표점은 여전히 "모델 출력 중 선택"
용도까지만이다 (8/28 오전 답변).

### 최종 경고 공지 (2026-08-28 운영국) — 질의 단계 종료

> "규정의 취지를 확대 해석하여 **우회하는 방식은 인정하지 않으며**, 모든 개별
> 상황을 사전에 구체적으로 규정해 드릴 수는 없습니다. ... 최종 허용 여부는
> 수상 후보 심사 시 **제출 코드를 기준으로 판정**하며, 판단 기준이 되는
> **베이스라인 코드도 이미 제공**되어 있습니다. ... 최종 결과에 대해서는
> **이의제기는 받지 않을 예정**입니다."

현재 리더보드 상위권에는 심사에서 걸러질 구조가 섞여 있을 가능성이 높다
(운영국도 9/9 공지에서 같은 취지로 언급했다).

**우리 원칙 (변경 없음, 더 단단해짐):**
- 회색지대 판단 기준 = "심사위원이 코드를 열었을 때 베이스라인의 확장으로 보이는가"
- 공격성은 합법 축에서: 학습량·깊이·격자·해상도·앙상블·추론 튜닝
- 탈락은 이의제기가 없다. 점수 몇 점보다 심사 생존이 입상의 전제다

### 그래서 우리 규칙

자차 상태나 목표 지점을 입력에 추가한 모델은 **제출 전에 반드시 영상 기여도를 측정한다.**

```bash
python tools/ablate_image.py <config> <checkpoint> --scenarios 10
```

영상을 0 으로 채우거나 다른 장면 영상으로 바꿔 넣고 L2 악화 폭을 잰다.
**악화가 20% 미만이면 그 모델은 영상을 안 보고 있다는 뜻이므로 제출하지 않는다.**
2차 재현성 평가에서 요구받을 가능성도 높으니 결과를 기록해 둘 것.

> 참고: 이 현상은 알려진 문제다.
> "Is Ego Status All You Need for Open-Loop End-to-End Autonomous Driving?" (CVPR 2024)

### 리더보드를 그대로 믿지 말 것

우리 측정치와 대조하면 이렇다.

| 리더보드 | 점수 | 우리가 측정한 대응물 |
|---|---|---|
| 1·2위 | 0.077 | 목표점 Hermite+운동학(0.166)보다도 낮다 |
| 3위 | 0.398 | 순수 운동학 외삽(0.414)과 거의 같다 |

정당한 방법으로 도달하기 어려운 값들이고, 공지가 나온 배경도 이것으로 보인다.
**상위권 점수를 목표로 잡지 말 것.** 같은 방식을 따라가면 우리도 실격이다.
정직한 카메라 기반 모델의 실제 성능선을 우리가 먼저 확보하는 게 목표다.

## 1. config 는 새 파일을 만들어 상속한다

공통 config 를 직접 고치면 4명이 매번 충돌한다. **바꾸는 부분만 적은 새 파일**을 만든다.

```
projects/configs/VAD/
├── VAD_etri_tiny.py           원본 (수정 금지)
├── VAD_etri_base.py           원본 (수정 금지)
├── VAD_etri_tiny_pre.py       전처리 데이터용 기준 (수정 시 팀에 공유)
├── exp_jeung_0815_bev150.py   ← 각자 여기에
├── exp_kim_0815_queue5.py
└── exp_lee_0816_base.py
```

### 명명 규칙

```
exp_<이름>_<MMDD>_<변경점>.py
```

### 작성 예

```python
# exp_jeung_0815_bev150.py
_base_ = ['./VAD_etri_tiny_pre.py']

bev_h_ = 150
bev_w_ = 150
fp16 = dict(loss_scale=512.)
data = dict(samples_per_gpu=6)
```

세 줄이면 충분하다. 나머지는 상속된다.

> 공통 코드(`projects/mmdet3d_plugin/`)를 고쳐야 할 때는 **먼저 팀에 알린다.**
> 모두의 실험에 영향을 준다.

## 2. 배치 크기는 GPU 에 맞춘다

| VRAM | 권장 | 근거 |
|---|---|---|
| 16 GB | **fp16 batch 6** | 11.9 GB 점유 |
| 12 GB | **fp16 batch 4** | 8.1 GB 점유 |
| 24 GB 이상 | batch 8 시도 | 논문 기준 실효 배치와 일치 |

**VRAM 을 90% 이상 쓰면 안 된다.** Windows/WSL 은 넘치면 에러 대신 시스템 RAM 으로
흘려보내며 **조용히 20배 느려진다.** (batch 8 을 16GB 에서 돌렸을 때 실측: 2.3초 → 43초)

학습이 이유 없이 느리면 `nvidia-smi` 로 VRAM 점유율부터 확인할 것.

> config 의 `lr=2e-4` 는 원래 **8 GPU × batch 1 = 실효 배치 8** 기준으로 맞춰진 값이다.
> 단일 GPU batch 1 은 의도된 설정에서 8배 벗어난 상태다. 배치를 키우는 건 속도뿐 아니라
> **학습 품질** 문제이기도 하다.

## 4. 자체 검증셋 — 사실상 우리 리더보드

제출이 5회뿐이므로 **자체 검증이 실질적인 리더보드 역할**을 한다.

### 확정된 분할 (변경 금지)

```
전체 376 시나리오  →  train 337 (101,100 샘플) / val 39 (11,700 샘플)
기준: 시나리오 단위, 수집 날짜별 비례 10%, seed=42
목록: docs/val_split.txt
```

| 날짜 | 전체 | val | | 날짜 | 전체 | val |
|---|---|---|---|---|---|---|
| 20260112 | 49 | 5 | | 20260212 | 12 | 1 |
| 20260113 | 10 | 1 | | 20260213 | 115 | 12 |
| 20260114 | 2 | 0 | | 20260219 | 33 | 3 |
| 20260120 | 5 | 1 | | 20260220 | 26 | 3 |
| 20260122 | 28 | 3 | | 20260303 | 6 | 1 |
| 20260205 | 19 | 2 | | 20260209 | 18 | 2 |
| 20260210 | 34 | 3 | | 20260211 | 19 | 2 |

**왜 이렇게 나눴는가**

- **시나리오 단위** — 프레임 단위로 섞으면 같은 장면의 인접 프레임이 train 과 val 에
  나뉘어 들어가 성능이 부풀려진다
- **날짜별 비례** — 특정 날짜를 통째로 val 로 빼면 그 구간을 학습에서 전혀 못 보게 되어
  결과가 왜곡된다. 14개 수집 세션에서 고르게 뽑았다
- **seed 고정** — 누가 다시 만들어도 같은 결과가 나온다 (`make_split.py`)

**이 분할을 바꾸면 이전 실험과 비교할 수 없다.** 바꿔야 할 이유가 생기면 팀 전체가
합의하고, 이후 모든 실험을 다시 돌려야 한다.

## 5. 장시간 학습

1 epoch 이 약 12시간이다. 터미널에 묶어두면 안 된다.

```bash
nohup docker exec etri python tools/train.py \
  projects/configs/VAD/exp_jeung_0815_bev150.py \
  --work-dir work_dirs/exp_jeung_0815_bev150 --no-validate \
  >> ~/logs/exp_jeung_0815_bev150.log 2>&1 &
```

진행 확인:

```bash
tail -f ~/logs/<실험명>.log
nvidia-smi
```

중단된 학습 이어서:

```bash
python tools/train.py <config> --work-dir <같은 경로> --resume-from <경로>/latest.pth
```

체크포인트는 **반드시 iteration 단위로 저장한다.**

```python
checkpoint_config = dict(by_epoch=False, interval=1000, max_keep_ckpts=3)
```

`interval=1` 은 "1 epoch 마다"라는 뜻이다. 1 epoch 이 11시간이 넘으므로 그 안에 죽으면
**아무것도 안 남는다.** 2026-08-18 밤에 실제로 iteration 2000(5시간 20분)에서
`CUDA error: unknown error` 로 죽었고 체크포인트가 없어 전부 날렸다.

`by_epoch=False, interval=1000` 이면 약 38분마다 저장된다. 258MB x 3 = 774MB 라 부담 없다.

### 죽어도 알아서 이어받게 하기

`tools/train_watch.sh` 가 학습이 죽으면 `latest.pth` 에서 재개해 다시 띄운다.
**컨테이너 밖(호스트 셸)에서** 실행한다.

```bash
setsid nohup bash tools/train_watch.sh <config이름> "data.samples_per_gpu=5" > /dev/null 2>&1 < /dev/null &
```

### 재개하면 그 epoch 의 남은 부분을 건너뛴다 (알고 쓸 것)

mmcv 1.4.0 의 `EpochBasedRunner` 는 체크포인트를 저장할 때 메타에
`epoch = 현재epoch + 1` 을 적는다. **epoch 중간에 저장해도 "이 epoch 은 끝났다"고
기록되므로**, 거기서 재개하면 남은 부분을 건너뛰고 다음 epoch 으로 간다.

2026-08-19 실측:

```
resumed epoch 1, iter 999
Epoch [2][100/20220]        <- epoch 1 이 6% 진행된 상태였는데 2 로 넘어감
lr: 2.000e-04 -> 1.951e-04  <- 코사인 스케줄도 한 칸 진행됨
```

가중치와 옵티마이저 상태는 보존되므로 학습이 망가지진 않는다. 다만:

- **재개할 때마다 epoch 을 하나씩 까먹는다**
- **학습률 스케줄이 그만큼 앞당겨진다**

그래서 이렇게 운영한다.

- 체크포인트는 그대로 iteration 단위로 자주 남긴다. **크래시 시 전멸을 막는 안전망**이다
- 학습 초반(첫 epoch 안)에 죽었으면 **차라리 처음부터 다시 돌린다.** 잃는 게 적다
- 후반에 죽어서 재개했다면 `runner.max_epochs` 를 재개 횟수만큼 올려 보상한다
- **기준점이 되는 베이스라인은 재개 이력이 없는 실행으로 확보한다**

### VRAM 은 90% 를 넘기지 말 것

2026-08-18 크래시 당시 VRAM 이 15,874 / 16,311 MiB (97.3%) 였다. 여유가 437MB 뿐이었고,
Chrome·VS Code 등 데스크톱 앱 30여개가 같은 GPU 를 쓰고 있었다.
WSL2 에서는 이때 WDDM 이 학습 컨텍스트를 밀어내면서 깔끔한 OOM 이 아니라
`unknown error` 로 죽을 수 있다. batch 를 하나 줄여 2GB 정도는 비워둘 것.

### 평가 지표 (2026-08-19 운영국 확정)

가이드라인 PDF 13쪽의 "6개 단순 평균"이 아니라 **사전설명회 자료 44쪽이 맞다.**

```
1초 L2 = 앞 2개 waypoint (0.5, 1.0초) 의 평균 변위(ADE)
2초 L2 = 앞 4개 (0.5 ~ 2.0초)
3초 L2 = 6개 전부
최종 L2_avg = 위 세 값의 평균          <- 리더보드 대상
```

베이스라인 코드가 이미 이대로 구현돼 있다 (`VAD.py:641`, `cur_time = (i+1)*2`).

이 정의는 waypoint 가중치를 크게 비튼다.

| waypoint | 0.5s | 1.0s | 1.5s | 2.0s | 2.5s | 3.0s |
|---|---|---|---|---|---|---|
| 실효 가중치 | 11/36 | 11/36 | 5/36 | 5/36 | 2/36 | 2/36 |
| 단순평균 대비 | ×1.83 | ×1.83 | ×0.83 | ×0.83 | ×0.33 | ×0.33 |

**0.5초와 1.0초 두 점이 점수의 61%를 차지한다.** 2.5·3.0초는 합쳐서 11%뿐이다.
먼 미래를 정확히 맞추려는 노력은 점수 기여가 작다.

> 학습 손실(`VAD_head.py:1139`)은 6개 waypoint 를 **균등하게** 취급한다.
> 지표에 맞춰 가중치를 `[11,11,5,5,2,2]` 로 주는 실험은 구조 변경 없이
> 지표를 직접 겨냥하는 후보다. 단 공용 코드 수정이므로 팀에 먼저 알릴 것.

### 형식

```json
{
  "__flops__": 446605899456,
  "<clip_hash>": [[x1,y1],[x2,y2],[x3,y3],[x4,y4],[x5,y5],[x6,y6]],
  ...
}
```

- 6점 = 미래 0.5 / 1.0 / 1.5 / 2.0 / 2.5 / 3.0 초의 **누적** waypoint
- 좌표계 = 현재 프레임 원점, x=전방 y=좌
- 다중모드 모델이라도 **궤적 1개**로 줄여서 제출
